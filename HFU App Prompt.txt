Build a production-quality, browser-based industrial petrophysics application called:

"HFA — Hydraulic Flow Analysis Suite"

Subtitle:
"Integrated Hydraulic Flow Unit, Petrophysics & Reservoir Quality Analysis"

The application must feel like a professional subsurface/petrophysics interpretation suite rather than a generic analytics dashboard.

============================================================
1. CORE PRODUCT PHILOSOPHY
============================================================

Build the application around a complete Hydraulic Flow Unit (HFU)
workflow:

Raw Well Data
    ↓
Data Import & QC
    ↓
Depth Matching / Core-Log Integration
    ↓
Petrophysical Parameter Calculation
    ↓
RQI / FZI / HFU Analysis
    ↓
Crossplots & Statistical Analysis
    ↓
HFU Clustering
    ↓
Regression / Feature Selection
    ↓
FZI Prediction from Logs
    ↓
Validation
    ↓
Depth-Based HFU Interpretation
    ↓
Reservoir Quality Summary
    ↓
Export / Report

The software should support single-well and multi-well workflows.

It must be optimized for large well-log datasets and should avoid
unnecessary memory usage.

IMPORTANT:
Do NOT send raw well-log data to a backend unless absolutely required.

Prefer:
- browser-side parsing
- Web Workers
- streaming/chunked processing
- typed arrays
- IndexedDB for temporary persistence
- lazy loading
- downsampling only for visualization
- statistical calculations on original-resolution data
- serverless architecture where possible

The application should work even if the user disconnects from the
internet after loading the application.

============================================================
3. MEMORY-EFFICIENT DATA ENGINE
============================================================

This is extremely important.

Design the application for large well datasets.

Use:

Web Workers
TypedArrays
Float32Array where precision permits
Float64Array for calculations requiring higher precision
IndexedDB
Chunked processing
Lazy curve loading
Virtualized tables

Never duplicate the complete dataset unnecessarily.

Architecture:

File
 ↓
Parser Worker
 ↓
Normalized Internal Well Model
 ↓
IndexedDB / in-memory chunk store
 ↓
Visualization Worker / UI
 ↓
Analysis Worker

Maintain metadata separately from numerical arrays.

Example internal structure:

Well
{
  id,
  name,
  uwi,
  metadata,
  depth: Float64Array,
  curves: {
      GR: Float32Array,
      RHOB: Float32Array,
      NPHI: Float32Array,
      RT: Float32Array
  },
  curveMetadata
}

Do NOT store the same curve simultaneously as:
- JavaScript arrays
- JSON
- DataFrames
- chart datasets

Use one canonical numerical representation.

For plotting, generate only the visible depth window.
